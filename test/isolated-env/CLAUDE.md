# test/isolated-env

Sandbox projects that install the built packages as `file:` dependencies and run them outside the workspace. The `file:` paths resolve only in the sibling-directory layout the `isolated-env` job of `.github/workflows/test.yml` builds; reproducing a failure locally needs that same layout.

- `pnpm-workspace.yaml` is the file pnpm reads for `overrides` and `allowBuilds`: when adding a local package to a sandbox's `dependencies`, add the matching `overrides` entry there (`packages/@markuplint/test-tools/src/isolated-env-manifests.spec.ts` fails until the two lists agree). Do not add a `pnpm` block to `package.json`; current pnpm ignores that block with only a warning (`The "pnpm" field in package.json is no longer read by pnpm`), so an override that exists only there does nothing: the `@markuplint/*` packages that `markuplint` depends on resolve to the registry instead of the local build, and the symptom is a single `config-error` violation (`Rule not found: <name>`) in place of the expected output.
- Several dependencies are deliberately `latest` (`@types/node`, `tsx`, `npm-run-all`) and pnpm is installed as `latest`, so a sandbox can break with no change in the PR. Triage before touching anything: compare with the previous green run on the base branch (`gh run view <id> --json jobs`), delete the job's cache (`gh cache list --key <prefix>`, then `gh cache delete <id>`) and re-run the whole workflow; a failure that survives the cache rebuild is dependency drift, not a flake. When the drifted dependency is one the root `package.json` pins, pin the sandbox to that same version (`typescript` is pinned for this reason). Such a fix may share the PR that hit it once the two checks above are on record.
